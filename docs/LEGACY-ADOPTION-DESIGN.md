# Legacy adoption during runtime upgrade

Status: peer-reviewed design for issue #43. The design is approved for implementation. Nothing
in this document is implemented yet. It does not authorize a change to a live installation.
This document is the one authoritative specification. It consolidates the design review on
issue #43, which ran as revision 1 and three amendments. Where this document and a review
comment differ, this document applies.

## Why this is part of #43

The issue text allows memory that the installation does not own to be refused and reported,
and the current operation does that correctly. This design widens the supported boundary
because [RUNTIME-UPGRADE-DESIGN.md](RUNTIME-UPGRADE-DESIGN.md) requires it:

- "A supported legacy/manual adapter must supply explicit inventory and process-exit
  evidence before those paths can pass preflight."
- "The complete #43 acceptance gate still includes manual-process coverage and cannot close
  on native-only implementation."

A run in scratch measured the gap. It used `main` at `35a8bdd`, the only published release,
installed by that release's own installer, and then upgraded with the current
`scripts/upgrade.py`:

- An install with no sessions and no memory upgrades. The configured state root must exist;
  #93 reports that condition.
- An install that runs `memory.py serve`, as the `main` README tells users to do, is refused:
  `unowned memory state found`.
- An install with a session directory under `state/sessions/<key>` is refused:
  `legacy or unfinished session requires an explicit upgrade adapter`.
- An upgraded prefix that has had one interactive command run under `umask 002` refuses the
  next upgrade: `unsafe manifest ancestor: PREFIX/koinon/__pycache__ (mode 0775)`.

The upgrade acceptance matrix starts from `86567be`, a development commit, so it cannot show
these results. The current installer also still creates two legacy shapes that its own
upgrade refuses: the `--thread` unit pair, and the legacy session flow used when no
`session_backend` is saved.

## Source arrangements

| Id | Arrangement | Generated by |
|---|---|---|
| L1 | Thread-only unit pair `koinon-notify.service` and `koinon-bridge.service` (or `codex-peer-notify` and `codex-peer-bridge`), enabled, with state at the state root and possibly no `install.json` | `main` `install.py --thread`; current `install.py` |
| L2 | Session unit `koinon-session-<key>.service` (or `codex-peer-session-<key>`) running `session.py run --thread T --repo R`, loaded and started but not enabled | `session.py ensure` with a reachable systemd user manager |
| L3 | Foreground `session.py run` from a printed `start_command` | `session.py ensure` returning `manual_required` (macOS, or no manager) |
| L4 | `memory.py --state-dir S --repo-path R serve`, run in a terminal or tmux, or supervised by a hand-written unit or plist | `main` README |
| L5 | Current manual session selection (`session_backend: manual`) | current installer; `upgrade_manual` refuses sessions today |

A foreground L1 is not a shape that `main` generated. It is refused.

## Operator opt-in

Adoption starts only when the operator asks for it:

```sh
python3 scripts/upgrade.py --prefix P --source S --adopt-legacy
```

Without `--adopt-legacy`, preflight runs the full inventory and every proof. It then refuses
before shutdown with `legacy_adoption_required`, and lists each legacy component with its id,
its proof status, its destination backend and the exact command. With the option, the adoption
is frozen into the plan and becomes part of the plan digest.

Two further opt-ins apply to individual components:

- `--adopt-memory-unit PATH` accepts an L4 hand-written unit or plist that has no Koinon
  marker.
- `--adopt-memory-repo PATH` names the repository of a stopped L4 store (see Identity).

## Ownership proof

The proof correlates independent evidence and never rests on one field. It is taken at
preflight and again under exclusion before the first stop. A difference refuses before
shutdown. A condition that cannot be established refuses before shutdown, and the refusal
names the condition and the remedy. Absence is never evidence.

### Unit-backed sources

- The on-disk definition passes `check_owned_unit`: it belongs to the owner, is not a symlink,
  carries a Koinon or `codex-peer-bridge` marker, and has an `ExecStart` that names this
  prefix. An unmarked L4 unit needs `--adopt-memory-unit`.
- The effective configuration comes from the manager:
  - systemd: `systemctl --user show` for `FragmentPath`, `DropInPaths`, `ExecStart`,
    `Environment`, `EnvironmentFiles`, `MainPID`, `LoadState`, `ActiveState`, `UnitFileState`,
    `TriggeredBy` and `Restart`.
  - launchd: `launchctl print gui/<uid>/<label>`.
- `FragmentPath` must be the file that was read. Drop-ins, environment files, or an effective
  `ExecStart` that differs from the file refuse with `unit_effective_config_differs`.
- The digest of the definition bytes is recorded. It is checked again at the stop and at the
  move-aside.

### Process identity

- The kernel pid and start marker come from `platform_support.proc_start`.
- Memory: the pid, generation and repository key in `hello` must equal those in `owner.json`
  and the kernel peer pid. `verify_running` performs this check, and `main` uses the same
  protocol. `verify_running` does not compare `store_id`. The `store_id` chain is a separate
  step (see Identity).
- Sessions: the bridge `status` pid must equal the kernel peer pid, and the notifier
  readiness `bridge_pid` must equal the bridge pid. For L2 and L3, the bridge and the notifier
  must be children of the `session.py run` process that holds `supervisor.lock`.

### Closure

Preflight builds the full closure before any component stops. The closure contains:

- for each unit or job, its triggers, its reverse dependencies, and every other unit whose
  effective `ExecStart` names this prefix;
- a collision check of every target unit name and launchd label against every systemd
  `UnitPath` directory and every launchd loading source.

A collision with a source definition that the move-aside will remove is expected, and is
recorded with that definition's digest. Any other collision refuses. A trigger or reverse
dependency that is not a proved component of this operation refuses with
`legacy_unit_triggered_externally`. Immediately before the first stop, a closure check
computes the closure again and requires it to equal the preflight closure.

### Unit states

systemd:

- Accepted source states: `LoadState=loaded` with `UnitFileState` of `enabled`, `disabled` or
  `linked`.
- `masked`, `masked-runtime`, `static`, `generated` and `transient` refuse with
  `legacy_unit_state_unsupported`. `main` generates none of them.
- The original `LoadState`, `UnitFileState`, `ActiveState`, `FragmentPath` and each
  enablement link with its target are stored in the plan.

launchd:

- The manager must be reachable (`launchctl print gui/<uid>`).
- Absence is the measured "could not find service" result of
  `launchctl print gui/<uid>/<label>`, identified by its exit status. If that status is not
  unique, absence also requires `launchctl list` to omit the label, in the same capture.
- A permission error or any other failure refuses, and is never counted as absence.

## Persistent exclusion

A repeated scan does not prove exclusion, and a lock is lost when the coordinator dies. Each
class of starter is therefore excluded by a durable on-disk condition that the old code
already refuses. Each barrier is set before the final scan.

### A1. Configuration barrier (session starters)

`main` `session.py` reads `install.json` with `json.loads` and indexes `config['state_root']`
in `details()`. It does this before it takes any lock and before `private_dir` creates any
directory. The current `runtime_names.install_config` refuses a missing or non-absolute
`state_root`.

The exclusion marker is therefore version 2. On activation, `state_root` and `unit_dir` move
under `upgrade.frozen`:

- every `main` session action exits before it creates state;
- every current reader refuses;
- the coordinator reads the frozen installation document instead.

The barrier survives coordinator death and reboot. It covers the `session.py ensure` that
`main`'s managed guidance runs in each new Codex conversation.

### A2. Schema barrier (memory starters)

`main` `memory.py` never reads `install.json`. Its `Store` sets exclusive locking and then
classifies and inspects the store before it configures anything. `inspect` refuses a schema
above 4 with `schema_too_new` and writes nothing.

A step called the seal migrates each store in place to schema 5 (see Seal). After the seal,
every `main` memory starter is refused by the store itself. This holds for a new starter, for
one that was waiting on `start.lock`, and for one that runs after coordinator death or after a
reboot. The seal protects only the memory store. Inbox and notifier writers are excluded only
by A1, the drain and A3.

### A3. Unit move-aside (unit-backed starters)

A disabled unit that is still loaded can be started by a dependency or a timer. Before the
backup, in the quiesce phase, the coordinator:

1. records the exact prior state (see Unit states);
2. stops the unit and waits for kernel death of the recorded `MainPID` and its children;
3. moves the definition and its enablement links into `<operation>/legacy-artifacts/`, with
   a journal record for each file;
4. runs `daemon-reload`, or confirms `bootout` on launchd.

The terminal observation during quiesce and backup must satisfy all of these:

- `systemctl --user show` succeeds, so a manager that cannot be reached is never taken as
  absence;
- `LoadState=not-found`;
- `ActiveState=inactive`;
- no enablement link remains.

On launchd the terminal observation is confirmed absence.

This observation depends on the phase. From `adopting` onward, a target artifact may use the
same name as a source unit (L2 source `koinon-session-<key>.service`, for example). For such
a name, the observation instead requires all of these:

- the frozen target artifact bytes;
- the target's effective configuration identity;
- the startup exclusion;
- the retained old definition under `legacy-artifacts/`;
- no old process.

Absence is required only for retired names.

### Drain of invocations that read the configuration before A1

A `main` `session.py` invocation or an installer that read the configuration before A1 can wait
and then act. The coordinator therefore:

1. publishes A1;
2. takes a process snapshot and records `pid` and `proc_start` for every same-euid process
   whose argv names this prefix's `session.py`, `scripts/install.py`, `bridge.py` or
   `notify.py`, other than the proved long-running components;
3. waits, for at most 120 s, until the kernel reports each recorded process dead with the
   same start marker. A process that is still alive at that bound, including a stopped one,
   refuses with `legacy_invocation_active` and names its pid, argv and parent chain. Nothing
   has been stopped at that point, A1 remains, and a resume repeats the drain;
4. proves every unit-backed source again (digest, effective configuration, active state),
   because a drained `ensure` may have rewritten or started a unit;
5. performs A3;
6. takes a second snapshot, which must show no process that is not proved or drained.

Barrier order:

1. preflight proof;
2. A1;
3. drain;
4. re-proof;
5. A3;
6. final snapshot;
7. owned stops;
8. backup;
9. seal.

### Concurrent installer or uninstaller: unsupported, detected

A1 does not exclude a `main` installer. That installer reads `previous.get('state_root')` with
a default, copies the runtime, and rewrites `install.json` without checking a marker. No
mechanism makes old code refuse it. Running an installer or an uninstaller of any version
against the prefix during an operation is therefore an unsupported external mutation. It is a
documented precondition of the upgrade, not a supported concurrent operation.

At every phase boundary, and immediately before each irreversible step, the coordinator checks
that the `install.json` bytes equal the marker bytes it wrote. It also checks that the prefix
manifest equals the state that the journal expects for that phase. The irreversible steps are
each seal, the start of `replacing`, each publication in `adopting`, and `finish()`. A
difference refuses with `external_installation_mutation`, which names the file and the phase.
After that refusal no irreversible step runs, and the report names the barrier that was
overwritten.

## Memory handover before the seal

`main` `serve` does not hold `start.lock` while it serves. Its `release()` takes `start.lock`
again on exit, so the coordinator cannot hold the lock across the stop. The handover is:

1. Record `pid` and `proc_start` from `owner.json`, send the stop request, and wait for
   `process_state == 'dead'`. The removal of `owner.json` alone is not enough.
2. Take `start.lock` without blocking, and retry within a bound.
3. While holding the lock, verify that the store is quiet:
   - no endpoint answers;
   - `owner.json` is absent or `owner_is_dead`;
   - the coordinator's own exclusive SQLite open succeeds.

   If a starter took the lock first and serves again, prove it again (same key, same
   `store_id`) and return to step 1. When the bound is exhausted, the upgrade refuses with
   `legacy_writer_restarted`, names the pid and parent chain, and keeps the barriers.
4. Keep `start.lock` through the backup and the seal. `capture.hold` already holds it.

All stores are sealed in one sub-step while every store's `start.lock` is held.

## Identity: expectations and evidence

The plan is immutable and holds the expectations:

- keys and threads;
- the `store_id` taken at preflight: from the live `hello` for a running source, or from the
  disposable online copy's `meta` for a stopped source;
- unit digests;
- target records and artifact digests.

Observed evidence is append-only, in write-once receipt documents:

- stop proofs;
- barrier records;
- drain records;
- backup `meta`;
- comparisons;
- seal receipts;
- moves;
- lock inodes;
- restorations.

The `store_id` chain must hold: preflight value, then retained backup `meta.store_id`, then
sealed store `meta.store_id`. For a stopped source, the proof before shutdown uses only the
disposable preflight copy that `database_check` already takes. The retained backup confirms
the proof afterwards and never replaces it.

A stopped memory store records only its repository key. Its common directory comes from
exactly one of these sources:

- a session record, or a unit argv, whose repository hashes to the key;
- the unit's `--repo-path`;
- `--adopt-memory-repo`.

When no source gives the directory, or sources disagree, the upgrade refuses with
`memory_repository_unresolved`.

Session identity:

- `session.json` has exactly `{thread, name, repo, agent, model}`;
- `sha256(thread)[:16]` equals the key;
- the unit or process argv names the same thread and repository.

A DeepSeek session without `dsh_url` refuses. The current `commands()` requires that field,
and `main` made it optional.

Supported source shapes, from the released schema contracts:

- memory schema 4;
- memory schema 3, which has no `store_id` because `main`'s `inspect` refuses one;
- inbox schemas 2, 3 and 4. `main` migrates 2 and 3 when it opens them, and `expected_inbox`
  gains declared 2→4 and 3→4 transitions;
- notifier journal schema 2;
- a `notify-cursor.json` from before the journal, through the existing migration.

## Before-image generations

Generation 0 is the plan's multi-component capture. It is taken after the drain and all owned
stops, and it is authoritative until it is invalidated.

Comparison, before the seal and again before `adopting`, per component:

- an unsealed component is compared with the authoritative capture, bytes and SQLite sidecars
  included;
- a sealed store is compared with its seal result receipt: the file digest after the
  `TRUNCATE` checkpoint, the sidecar state and the semantic digest. The migration's own
  changes are the declared expectation and are never reported as intervening writes.

A difference invalidates the generation:

- an `invalidated` receipt records the component and its semantic difference;
- the upgrade refuses with `before_image_invalidated`, naming the component, the writer when
  it is known, and the difference in head, floor, cursor, entry and work-item counts;
- nothing retries silently.

`--resume DIR --plan DIGEST --rebase-before-image` is the only way to continue. It:

1. proves every component again;
2. quiesces again any component that restarted;
3. takes a complete multi-component capture as generation N+1, never a patch of one component;
4. computes the new expectations;
5. writes an amended plan whose digest chains to the previous digest, and prints the new
   digest.

Every earlier generation and receipt is kept. The completion report names the authoritative
generation. It lists the difference between generation 0 and that generation as intervening
writes by the named writer.

Rebase is forbidden once any seal has committed. An attempt refuses with `rebase_after_seal`,
because a new capture would replace the only rollback image from before the migration. An
invalidation after a seal refuses with `before_image_invalidated_after_seal`, and the barriers
remain.

The only way on from that state is the explicit restoration of the sealed stores from the
authoritative generation. The restoration appends a verified restoration receipt, which opens
a new recovery epoch. That epoch supersedes the seal receipts for resume decisions and deletes
no history. Rebase becomes legal again only when all of these hold:

- every relevant sealed store is restored;
- every restored store is verified under exclusion;
- no writes have been released.

A pre-seal state is never inferred from the schema bytes while an older result receipt remains
authoritative. Nothing restores automatically.

## Seal

The seal moves the irreversible schema transition ahead of the runtime replacement. From the
seal onward, rollback means restoration from the backup generation. That is already true after
any start at schema 5; the seal only makes it happen earlier. The barrier needs the seal.

For each store, in key order:

1. Schema 3 only: mint the `store_id` and persist it in a `seal-identity` receipt.
2. Run the migration trial on a disposable copy of the retained backup, passing that same
   `store_id` as a parameter. The migration code gains the parameter for this, and only the
   seal uses it. The trial therefore matches the real migration, and no second UUID is ever
   minted.
3. Write the intent receipt. It records:
   - the key and the generation;
   - the source schema;
   - the source `store_id`, which is the preserved value for schema 4, or null for schema 3
     with a reference to `seal-identity`;
   - the target `store_id`;
   - the expected post-migration semantic digest;
   - the preimage byte digests from the capture.
4. Migrate through the existing gated migration path with index and sweep work deferred. This
   is the function that `expected_memory` runs on the trial copy, so no maintenance escapes
   the declared expectations. The migration:
   - runs as one SQLite transaction;
   - uses `synchronous=FULL`;
   - writes the schema version last;
   - after the commit, checkpoints with `TRUNCATE` and fsyncs the database, the WAL and the
     directory.
5. Write the result receipt: the observed semantic digest, the file digests and the
   `store_id`.

Resume decision for each store, in the current recovery epoch:

| Receipts | Store state | Action |
|---|---|---|
| no intent | at source schema | The store must equal the captured preimage byte for byte; otherwise see Before-image generations. |
| intent | at source schema | The migration did not commit. The store must equal the captured preimage byte for byte; then migrate again with the same intent. |
| intent, no result | schema 5 | Accept only if the semantic digest and `store_id` equal the intent; write the missing result receipt. Otherwise refuse with `seal_unexpected_state`. |
| intent and result | schema 5 | Verify the result receipt again. |

A sealed store is never sealed again, and never restored automatically, even when another store
in the same operation is still unsealed. A partial seal is a normal crash state, and a resume
continues it. After the first seal, every barrier stays in place until release.

## Destination

Each source becomes the owned selection that a fresh install creates:

- systemd on Linux when a user manager is reachable;
- launchd on macOS;
- manual otherwise.

The destination records are built by the new source's existing builders:

- sessions: `session_service_config.selection` and `session_service_artifacts.publish`;
- memory: the `component_install` selection and `memory_service_artifacts.publish`.

Other properties of the destination:

- The session name and thread are preserved.
- Memory is adopted in place. Both branches derive `state_root/memory/<key>` in the same way.
- L5, and L3 on a host without a manager, need a manual session handoff. It parallels the
  memory handoff in `upgrade_manual`: exit 75, the exact `argv`, and a resume that joins
  kernel identity, supervisor generation and pair readiness.

### L1 layout move

L1 keeps its state at the state root. Its target is `state_root/sessions/<sha256(thread)[:16]>`.

Identity:

- thread, name and repo come from the proved notifier unit argv;
- the agent is `codex` and the model is null;
- `notify-cursor.json` must name the same thread;
- the target `session.json` is frozen in the plan.

File inventory:

- The inventory is derived from the `main` code, together with fixtures that run `main`'s own
  L1 path through delivery, memory binding, a notifier migration from a cursor file, a health
  failure and a restart.
- The union of those observations is pinned by a test.
- An entry outside the inventory refuses with `legacy_state_unrecognized`.

References:

- Every absolute path stored in the inbox and journal databases is enumerated, and a test
  checks that the move does not affect it.
- An unexpected reference to the state directory refuses.

The move:

- Each file is renamed within the state root, on the same filesystem.
- It is journaled per file: an intent `{src, dst, dev, ino, sha256}`, the rename, then a
  result.
- A resume accepts the identity at `src` or at `dst`, never at both.
- Moves happen in `adopting`, after the backup.
- The migration expectation maps source paths to target paths.

Lock files are not moved as data:

- The coordinator holds the source `notifier.lock` and any `supervisor.lock`.
- In `adopting` it creates fresh target lock files and records both sets of inodes.
- The account-wide participant lock depends on the agent and the thread, not on the path.
- The source lock files move into `legacy-artifacts/` in `finish()`, after their inodes are
  verified.

## Coordinator changes

Plan:

- The plan version is incremented.
- New frozen documents: `legacy` (sources and expectations) and `target_installation` (the
  exact `install.json` after adoption, and every target record and artifact digest).
- `_components` accepts the kinds `legacy_session`, `legacy_pair` and `legacy_memory`, each
  with an explicit target.
- For an L1 install with no `install.json`, the target is built from the proved unit argv
  (`--state-dir`, `--thread`, `--name`, `--repo`, `--codex`), never from defaults.

Journal:

- A new `adoption-progress.json`, shaped like `replacement-progress.json`, records an intent
  before, and a result after, each of these:
  - barrier set;
  - drain;
  - unit move-aside;
  - seal;
  - L1 file move;
  - cache quarantine;
  - target publication;
  - lock release;
  - restoration.
- A resume reconciles each item against its identity.
- After a crash between a move-aside (quiesce) and its publication (`adopting`), the component
  has no definition and no selection, and A1 protects it. A resume continues from the journal.
  The documented explicit restoration uses the same journal.

Phases:

- The quiesce phases gain A1, the drain, the re-proof, A3 and the final snapshot.
- `backing_up` ends with the seal sub-step.
- A new `adopting` phase follows `replacing`. It holds the L1 moves and the target
  publication.
- `LAST_STEP` becomes 21.

Retained version-1 operations:

- `--resume` runs the operation's own recovery bundle with `-I`, and new code never interprets
  a version-1 plan.
- A test resumes a version-1 operation while a version-2 source is present.

Release order:

1. Publish the target artifacts and records, `pending` then `installed`, while marker v2
   remains. The current code refuses to start them outside the gated path.
2. Release the locks and start the gated targets (see Lock handover).
3. Check readiness.
4. Compare preservation against the expectations.
5. Release.
6. `finish()` commits `target_installation` as the last write, which removes A1.

Late failure: the barriers stay in place. The report names the explicit, gated recovery:
restore from the named generation, and restore the moved-aside definitions from the journal.

## Lock handover at gated start

`flock` is exclusive, so the coordinator cannot hold a lock until the target acquires it. At the
handover, the barriers exclude legacy starters; the locks do not.

From quiesce until `starting_gated`, the coordinator holds these locks for capture consistency:

- per session: the source `supervisor.lock` and `notifier.lock`. For L2 and L3 these are also
  the target files; for L1 the target files are journaled separately;
- the account-wide participant lock;
- per store: `start.lock`, `supervisor.lock` and `manager.lock`.

For each component, in the existing `_order` (memory first, then sessions):

1. Verify every barrier:
   - A1, by the marker bytes;
   - A3, by absence for retired names, or by the target identity for same-name targets;
   - the drain receipt;
   - for memory, the seal result.
2. Verify the journaled lock inodes, then release the component's locks, then the participant
   lock.
3. Start the gated target, which takes its own locks.
4. Verify that the target owner record names the journaled lock inodes.

No legacy starter can take a released lock:

- `main` session starters exit on A1 before they touch a lock;
- unit-backed starters are gone (A3);
- the drain has already completed;
- a `main` memory starter that takes `start.lock` meets schema 5 and exits;
- a concurrent installer is detected, not excluded.

## Bytecode trust

- **G1. Coordinator reads.** The coordinator and each subprocess it starts read bytecode only
  from a private per-operation `pycache_prefix`, beginning with the first project import:
  - `scripts/upgrade.py` is a bootstrap that uses only the standard library. Before any
    project import it sets `sys.pycache_prefix` to a fresh 0700 `mkdtemp` directory and sets
    `sys.dont_write_bytecode`;
  - every subprocess runs with `-I -X pycache_prefix=<operation>/pycache`;
  - the recovery bundle runs from a zip archive, which never consults `__pycache__`.

  `-B` and `dont_write_bytecode` only suppress writing. `pycache_prefix` redirects reading,
  because `cache_from_source` resolves under it. The installer bootstraps in the same way, and
  so G1 also covers the source checkout's caches, which are not validated.
- **G2. No new unsafe caches.** Each entrypoint runs `os.umask(0o077)` as its first
  statement, before any project import. Today the umask is set after the imports, and
  `memory_service.py` and `usage_report.py` never set it. G2 prevents the creation of unsafe
  caches. It does not make an existing cache safe.
- **G3. Ordinary command reads.** Each entrypoint runs as `__main__` and is never cached.
  Before its first project import, a few inline standard-library lines `lstat` these
  directories:
  - `PREFIX/__pycache__`;
  - `PREFIX/koinon/__pycache__`;
  - `PREFIX/scripts/__pycache__`.

  If any of them exists and is not an owned, private, no-follow directory, the lines set
  `sys.pycache_prefix` to a fresh `mkdtemp` directory and set `sys.dont_write_bytecode`. The
  check is inline because a shared helper module would itself load from the cache in
  question.
- **G4. Removal.** In `replacing`, after the owned shutdown, the coordinator moves each
  group-writable or other-writable cache directory that sits next to a selected source into
  `<prefix>/.upgrade/<operation>/untrusted-cache/`, on the same filesystem.
  - The directory must be a no-follow owned directory, identified by `dev` and `ino` before
    and after the move.
  - Its entries must be regular files named `<module>.<tag>[.opt-N].pyc`, for a selected or
    retired source, with at most 64 entries. Any other entry refuses with
    `untrusted_cache_contents`, which names the entry.
  - The move is journaled: intent, rename, result. A resume accepts the identity at the source
    or at the destination.
- **Version-1 operations.** First measure how the actual version-1 bundle and its subprocesses
  import. If they can read prefix caches, the dispatcher refuses to pass a resume to a
  version-1 bundle while an untrusted cache exists, with `v1_recovery_cache_untrusted`. The
  supported remedy is:

  ```sh
  scripts/upgrade.py --quarantine-untrusted-cache --resume DIR --plan DIGEST
  ```

  It runs the G4 quarantine under that operation's exclusion lock. If the measurement shows
  that version 1 never reads prefix caches, the exception is documented as unnecessary, with
  the evidence. This path is supported only after its tests pass.

## Installer: one ownership model

- `install.py --thread` still parses and still works. It stages an owned session selection,
  not the legacy pair.
- `session.py ensure` with no saved `session_backend` selects a backend (systemd or launchd
  when a manager is reachable, manual otherwise) and stages an owned selection.
- On an existing legacy installation, `ensure` and `install.py` refuse with
  `legacy_installation_requires_upgrade`, which names `scripts/upgrade.py --adopt-legacy`.
  They never reconfigure it silently.
- The legacy renderers remain only as the parsers that the adapter reads.

## Acceptance tests

Every test is deterministic. Fixtures install `main` at
`35a8bdd709fd262d63a1e38ab50a2e5525ae3622` with its own installer. The existing `86567be` matrix
remains for the newer development schemas.

Linux and systemd, each with `--interrupt-phase all`:

- L1 in these states: running, stopped, and enabled but stopped;
- L2 with L4 from a foreground parent;
- L2 with L4 from a hand-written unit (`--adopt-memory-unit`);
- L2 with a stopped L4 whose repository is resolved from a session record, and again from
  `--adopt-memory-repo`;
- L5 through the manual session handoff.

macOS and launchd: L3 with a foreground L4, going to launchd, in the running and stopped states,
with `--interrupt-phase all`.

Every case checks:

- `store_id`, head, floor and consumer cursors;
- inbox bindings and delivery acknowledgements;
- notifier checkpoints;
- the exact thread target and peer name;
- that the old definitions are retained;
- that no legacy process remains.

Exclusion and handover:

- a `main` memory starter that arrives after the final snapshot and blocks on `start.lock`
  exits with `schema_too_new` after the seal, and the store bytes do not change;
- a starter that wins `start.lock` in the stop window gets a repeated stop, and when the bound
  is exhausted, `legacy_writer_restarted`;
- the coordinator is killed with `SIGKILL` while a starter waits, once before and once after
  the seal;
- `main` `ensure` is paused after `details()` and before the lifecycle lock, and `main` `run`
  is paused before `supervisor.lock`. Each is resumed across A1 publication, across
  coordinator death and across target startup. A process still paused at the bound gives
  `legacy_invocation_active`;
- `main` `ensure` and `run` under marker v2 exit before they create a file, checked by a
  directory listing;
- a timer-triggered unit, and a unit with an external reverse dependency, refuse before
  shutdown;
- one test for each accepted and each refused unit state;
- the launchd absence status is measured and pinned;
- a same-name target replaces an L2 source unit, and the phase-aware A3 observation accepts
  it;
- a real gated target starts on systemd and on launchd, with `main` `ensure` and `run`, unit
  start and memory `serve` all attempted in the handover window. The target must hold the
  journaled lock inodes;
- the `main` installer and uninstaller are run after A1, between seals, during `replacing`
  and before `finish()`. Each gives `external_installation_mutation`, and no later
  irreversible step runs.

Seal and generations:

- death before the SQLite commit, after the commit but before the result receipt, and between
  the seals of two stores;
- recovery of a schema-3 store with its minted `store_id`, and no second UUID;
- a schema-5 store with unrelated writes gives `seal_unexpected_state`;
- an unsealed store is invalidated after a seal, which gives
  `before_image_invalidated_after_seal`, then explicit restoration with a new epoch, then a
  legal rebase;
- `rebase_after_seal` refuses;
- a rebase before any seal produces a chained plan and keeps the older generations.

Layout, journal and compatibility:

- L1 moves interrupted at every file;
- the closed-inventory refusal;
- the reference enumeration;
- exact restoration of moved-aside definitions, enablement links and loaded state;
- resume of a version-1 operation.

Bytecode:

- G1: a valid poisoned `.pyc` with a sentinel is never executed during an upgrade with every
  interruption, or during a failure and resume;
- G2: under `umask 002`, each entrypoint creates only 0700 cache directories;
- G3: each entrypoint runs with a poisoned 0775 cache and the sentinel never fires;
- G4: quarantine after completion;
- the version-1 cache path.

Refusals, each before shutdown:

- `legacy_adoption_required`;
- `unit_effective_config_differs`;
- `memory_repository_unresolved`;
- a missing `dsh_url`;
- an unmarked unit without the opt-in;
- `legacy_state_unrecognized`;
- `untrusted_cache_contents`.

## Out of scope

- Other users, and system service managers.
- Opaque wrapper scripts that start a legacy process indirectly. They refuse by name.
- A change of interpreter path. It needs its own adapter; see RUNTIME-UPGRADE-DESIGN.md.
